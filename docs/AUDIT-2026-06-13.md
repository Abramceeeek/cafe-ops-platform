## 🔴 CRITICAL (1, new — hand-verified)

### NC-1 — Courier can empty an order during the `in_transit` handoff (C2 on a second path)
`supabase/migrations/0038_change_order_status_rpc.sql:60-79` · confidence: high · **hand-verified**

`change_order_status` (SECURITY DEFINER, granted to `authenticated`) lets a `courier` transitioning
`ready_for_courier → in_transit` pass `p_removed_item_ids`; line 63 `DELETE`s those `order_items`, and the status
UPDATE at 74-79 proceeds with **no check that any line remains**. A courier can delete every item and still mark the
order in_transit (then delivered). This is the exact C2 vulnerability — but the C2 fix (`0041`) only guarded
`specialist_review`, not this RPC.
**Impact:** zero-item orders break receipt totals (GBP) and fulfilment; enables silent courier removal/fraud.
**Precondition:** a valid courier account (not anonymous/remote).
**Fix:** after the edit loop (before the UPDATE), add
`IF NOT EXISTS (SELECT 1 FROM public.order_items WHERE order_id = p_order_id AND quantity > 0) THEN RAISE EXCEPTION 'cannot_transition_empty_order'; END IF;`

## 🟠 HIGH (11 confirmed)

**Notifications (this branch's focus — hardest-audited):**
- **H1 — Notify routes have no error handling.** `notify-order/cutoff/pickup/overdue` wrap multiple `await`
  Supabase queries + `sendPush` with **no try-catch**. Any failure → unhandled 500, empty body; the webhook/cron
  may not retry → **silent notification loss, no logging**. Wrap each handler; log; return `{error:'internal'}` 500.
- **H2 — `sendPush()` throws if `FIREBASE_SERVICE_ACCOUNT` unset** (`lib/fcm.ts:10-12`), and no route catches it.
  A missing/misconfigured Vercel env var crashes every notify route. Fail fast at init, or try-catch per route.
- **H3 — Notify routes have no rate limiting.** Only `x-notify-secret` gates them; the secret lives in the
  webhook SQL (`orders_notify_webhook.sql:31`) and cron jobs. If it leaks, an attacker can spam every device and
  exhaust FCM quota. Add a per-call recipient cap + per-secret/min throttle (consider short-lived HMAC vs fixed secret).

**Ops scripts:**
- **H4 — `scripts/apply-sql.mjs` runs arbitrary SQL with no guard** (recurring H15). Reads any `.sql` and
  `client.query(sql)` against live — no `assertConfirmedTarget()`, no dry-run. A swapped `keys.txt` + a `DROP` file
  = irreversible prod loss. Add the project-ref guard the other destructive scripts already use; add `--dry-run`.
- **H5 — `apps/admin_web/scripts/detailed-e2e.mjs:13` hardcodes `Hubsync123!`** and (verifier corrected the
  reviewer) it **is reachable** — `login()` runs at lines 42-46 before the early halt. Missed by the `c10ea68`
  password sweep. Replace with `process.env.DEMO_PASSWORD` (exit if unset) or delete the dead test.

**CI / config:**
- **H6 — `migration-guard.sh` does not detect duplicate migration numbers.** It enforces immutability + `.sql`
  ext only; the four `0040*/0041*` files sail through. Add a duplicate-prefix check (snippet in source finding).

**Spec drift / missing features:**
- **H7 — Two-way handshake's "Final Confirm" was removed in code but the spec still documents it as mandatory.**
  `specialist_approved → shop_confirmed` has no UI/RPC path (commits `df467a5`/`45d5e70`/`c59d540` dropped it);
  `shop_confirmed` is an orphan enum value. `PROJECT_SPEC.md §7/§8.1 Step 3/§13` and ROADMAP task 2.4
  (`awaiting_confirmation_screen.dart`) describe a button that doesn't exist. **This is a doc fix, not a code bug**
  — update the spec to the actual 2-step flow (or re-add the step if product intent changed). Resolves prior C3.
- **H8 — Offline mode (Drift SQLite cache) is fully spec'd but not implemented.** `PROJECT_SPEC.md §14` +
  ROADMAP §0.1/§2.1 promise 30-day order/catalog/cutoff caching + offline banner; `shop_app/pubspec.yaml` has no
  `drift`/`sqlite` dep and no `drift_catalog.dart`. Either implement or descope to Phase 2 in the docs.

**Cross-layer consistency:**
- **H9 — `pastry_chef` role exists in SQL + Dart + RPCs but is missing from TS (`lib/roles.ts`).** A pastry_chef
  can be authorized by `specialist_review`/`change_order_status` (0041:32, 0038:42) but the web can't create them,
  shows them unlabeled, and hides their specialist tabs/notifications (`mobile-shell.tsx`, `app-shell.tsx`,
  `notification-bell.tsx` hardcode 2 roles). Either add pastry_chef to the TS constants or remove it from SQL/RPCs.

**Edge-function test coverage:**
- **H10 — `order-state-change` (the critical mobile state-machine handler) has zero tests**; all `*.test.ts`
  cover only pure `lib` helpers, never the handlers' auth/transition/pricing/Supabase paths. Add handler
  integration tests (happy path, auth failures, invalid transitions, malformed input, remove-all-items).
- **H11 — `generate-receipt` assumes `order_item_modifiers` is always an array** (`index.ts:108` `.map()` after an
  `as unknown as` cast). If the nested relation is null (RLS/schema drift), receipt gen crashes. Use `?? []`.

## Reconciliation notes (where verifiers overruled a finder/critic)

- **Duplicate `0040`/`0041` migration numbers are NOT a deployment-blocking CRITICAL.** The completeness-critic
  flagged it CRITICAL ("CLI may apply out of order/skip"), but an independent verifier refuted that: Supabase CLI
  sorts **lexically by full filename** (deterministic), and `docs/AUDIT-2026-06-11.md` records C1/C2 were already
  applied live and verified. Net: real **hygiene + CI-gap** problem (→ H6 + a MEDIUM), not a correctness break.
  Still worth renumbering the audit-fix files to `0042`/`0043`.
- **`order_items.unit_cost` nullable does NOT break receipts** — `generate-receipt/lib.ts:30-35` renders `"-"` for
  unpriced lines and gates the GBP total on `hasCosts`. (The real constraint gap is `products.price` NOT NULL.)
